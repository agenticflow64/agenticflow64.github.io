  • Полная индексация страниц (SSR), обновление прода — деплой по тегу через CI

Интернет-магазин в Telegram Mini App

Пет-проект

Магазин, который живёт внутри Telegram: без сайта-витрины и регистрации. Пользователь пишет боту, открывает Mini App и сразу заказывает; владелец ведёт каталог в админке.

Решение

  • Backend на Kotlin + Spring Boot 3: 37 REST-эндпоинтов, схема БД под Flyway, Swagger UI из коробки.
  • Авторизация без паролей: проверка подписи Telegram InitData (HMAC-SHA256) и своя пара JWT, роли USER и ADMIN.
  • Витрина на React 19: каталог с фильтрами, корзина, отзывы с фото, оплата картой/наличными/Telegram Stars; поиск на Elasticsearch.
  • Админ-панель: аналитика заказов, топ товаров, CRUD каталога с загрузкой фото.

Результат

  • Сквозной сценарий бот → Mini App → каталог → корзина → заказ → отзыв, без единого экрана регистрации
  • 7 сервисов поднимаются одной командой docker compose up
  • Демо-каталог: 8 категорий, 45 товаров с атрибутами

Бот приёма заказов на n8n + LLM

Демо-стенд

Малый сервис получает заказы в Telegram «как попало»: опечатки, капс, половина данных отсутствует. Нужно: свободный текст → структура в панели управления + понятное подтверждение клиенту, без ручного разбора диспетчером.

Решение

  • n8n-конвейер с двумя каналами приёма: живой Telegram-бот (собранный long polling) и веб-эмулятор чата для демо без телефона.
  • LLM с жёстким промптом «свободный текст → строгий JSON»: услуга, детали, срочность, имя, контакт, признак валидности.
  • Надёжность: не распознано — автоповтор через 3 с, вторая неудача — эскалация оператору; клиент никогда не остаётся без ответа.
  • FastAPI + SQLite: pydantic-валидация, дедупликация повторов по хэшу, жизненный цикл заказа; админка с фильтрами и статусами.

Результат

  • Извлечение всех полей на 12 реалистичных сообщениях с опечатками: 12/12 (100%)
  • Полный цикл «сообщение → заказ в БД → подтверждение»: ~21 с
  • Тесты pytest (API + e2e): 23 passed
  • LLM-часть на бесплатных моделях: себестоимость обработки 0 ₽

RAG-ассистент по базе знаний поддержки

Демо-стенд

Первая линия поддержки ищет ответы по чатам и таблицам. Нужен ассистент, который отвечает по внутренним регламентам, всегда даёт ссылку на раздел и честно отказывается, когда ответа в базе нет.

Решение

  • Конвейер: 29 документов базы знаний → чанкинг по заголовкам → эмбеддинги bge-m3 локально на GPU → PostgreSQL + pgvector с HNSW-индексом.
  • Порог релевантности 0.45 откалиброван на реальных скорах: вопросы вне базы → корректный отказ вместо выдумки.
  • Ответы со ссылками на документы; авто-fallback LLM-провайдера (основной → резерв).
  • Веб-интерфейс как рабочее окно поддержки: вопросы за смену слева, ответ с источниками справа.

Результат

  • Hit rate источника: 100% (16/16); корректные отказы вне базы: 100% (4/4), ложных отказов 0
  • Retrieval: 0,02 с (медиана); полный ответ — 4,9 с медиана на бесплатном тарифе LLM
  • Ингест: 29 документов → 151 чанк за 14 с на GPU
  • Тесты: 13 unit + 8 integration — зелёные

AI-ассистент ветеринарной клиники

Демо-стенд

Телефон — единственный канал клиники: администратор вручную отвечает на «сколько стоит…» и записывает данные. AI-виджет закрывает три сценария: ответы по прайсу, триаж срочности, запись на приём из живого диалога.

Решение

  • RAG по публичному прайсу клиники: 347 услуг, категории восстановлены детерминированными правилами, поиск по косинусной близости.
  • Эмбеддинги bge-m3 отдельным процессом на GPU — без GPU-зависимостей в сервисе; полный ингест ~5 с.
  • Оркестрация без фреймворков: классификатор намерения → ответы / триаж / запись; дисклеймер триажа на уровне бэкенда, а не LLM.
  • Виджет в стиле сайта клиники + админка заявок со статусами; только бесплатные LLM с fallback-цепочкой.

Результат

  • Поиск по прайсу: 11/12 (92%) top-1, 12/12 top-3; LLM назвал точную цену: 12/12
  • Триаж: 3/3 сценария — верный уровень срочности
  • Ингест 347 услуг с эмбеддингами: ~5 с (GPU)
  • Тесты pytest (офлайн): 30 passed

Агент-оркестратор заявок

Демо-стенд

Менеджер вручную читает заявки из Telegram, сортирует по типам и срочности, переносит в таблицу. Медленно, заявки теряются, спам съедает время.

Решение

  • Конвейер: Telegram-webhook (Bot API) или веб-форма → LLM-классификация (тип, срочность, извлечение имени и контакта) → реестр → уведомление; спам подавляется.
  • Цепочка fallback: бесплатная LLM → детерминированные regex-правила — сервис работает даже при недоступности API.
  • Веб-дашборд: реестр плотной таблицей, срочность цветом, фильтры, статусы, CSV-экспорт, автообновление.
  • Docker Compose одной командой; n8n — опциональным профилем для визуальной оркестрации.

Результат

  • Классификация на тестовом наборе: тип 15/15, срочность 15/15, извлечение полей 30/30
  • End-to-end от заявки до записи и уведомления: ~2,8 с
  • Regex-fallback: 15/15, <1 мс — страховка при падении API
  • Тесты: 21 passed (unit + webhook + экспорт)

Мониторинг-агент с объяснением алертов

Демо-стенд

Обычный мониторинг шлёт сырые алерты вида «node_filesystem_avail < порога». Нужен слой, который превращает алерт в понятное объяснение с планом действий.

Решение

  • Prometheus + Alertmanager → агент на FastAPI: cooldown-группировка всплесков, сбор контекста (метрики + логи Loki).
  • LLM-объяснение на русском по схеме «Что случилось / Вероятная причина / Что проверить».
  • Цепочка с ретраями: бесплатная LLM → rule-based fallback (сработал реально при сетевом сбое).
  • Веб-лента «сырой алерт → объяснение», демо-инциденты одной командой make, Grafana с автопровижинингом.

Результат

  • ServiceDown: алерт → уведомление с объяснением ~105 с, конвейер агента 11 с
  • Разбор инцидента по чек-листу агента: 5–15 с против 1,5–3 мин вручную (сценарная оценка)
  • Тесты: 18 unit + 2 integration smoke — зелёные

SKD — платформа агрегации контента и персональных лент

Пет-проект

Контент размазан по десяткам Telegram-каналов и сайтов, повторы прилетают по три-четыре раза. Платформа сама собирает посты, схлопывает повторы, понимает тематику и собирает каждому пользователю свою ленту.

Решение

  • Монорепо из подсистем вокруг общей плоскости данных: контент-пайплайн на Kotlin/Spring, GPU-воркер дедупликации (BGE-M3, классификатор EXACT/DUPLICATE/RELATED), рекомендательный сервис на FastAPI.
  • Платформа из шести микросервисов: шлюз с JWT, rate limiting и HMAC-подписью, события через Kafka (transactional outbox).
  • PostgreSQL 17 + pgvector с HNSW-индексами и замерами «до/после»; помесячное партиционирование, миграции Liquibase и Alembic.
  • Полный стек (11 сервисов) поднимается одним docker compose up; есть манифесты для Kubernetes; Flutter-клиент для Android и Web.

Результат

  • Работающий end-to-end конвейер: источник → парсинг → дедупликация → NLP → персональная лента, с e2e-тестом полного цикла
  • Порядка 630 автотестов в ML-подсистемах (dedup ~180, rec-system ~450) на Testcontainers
  • Ранжирование с разбивкой скоринга: вклад каждой компоненты можно объяснить построчно
